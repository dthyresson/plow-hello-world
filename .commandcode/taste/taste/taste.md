# Taste
- On macOS, prefers to install/manage CLI tools via Homebrew (e.g., removing an old manual install and reinstalling through brew) rather than downloading standalone installers. Confidence: 0.65
- When exploring an unfamiliar tool/API, prefers an explanation of options and tradeoffs first — explicitly says not to build or scaffold code ("don't build, just explain") and wants to be offered a plan before implementation. Confidence: 0.7
- Wants to verify things locally before anything is deployed or pushed; asks about local testing paths even for "hello world" experiments. Confidence: 0.55
- Asks for the simplest possible path ("what if I just wanted a simple hello world") and appreciates recommendations that minimize the diff instead of over-engineering. Confidence: 0.6
- Prefers project code to live in the current working directory (the project's own repo/folder) rather than in a separate sibling checkout — expects scaffolded code to land where they're already working. Confidence: 0.5
- Wants setup, usage, and code changes written up as documentation, not just delivered as code — explicitly asks for a README.md covering setup, how to launch/run everything, and how to test it, and confirms new features/config should be documented too ("yes document"). Confidence: 0.65
- Prefers documentation organized into focused, digestible pieces rather than crammed into one wall of text — happy with separate topic files (HOW-IT-WORKS.md, LIFECYCLE.md) but equally content adding a new topic as a section inside the existing README, placed next to related content, when offered the choice ("explain and document this in a section in readme under Latch" instead of a standalone LATCH.md). Confidence: 0.5
- Wants documentation to include the underlying concept, not just commands — asks for "what is X and how it works / how it's used" explanations (e.g., what GHCR is and how Plow uses it: distribution vs. execution, tag vs. digest) alongside the practical steps. Confidence: 0.55
- Values runtime observability: expects programs to log what they're doing and wants a clear way to watch/tail those logs (e.g., "can the agent log and how do I tail logs") rather than treating logging as an afterthought. Confidence: 0.45
- Cost/resource-conscious: before adopting a hosted service, asks whether it consumes compute minutes or quota ("does using GHCR run compute against my GitHub usage?") and wants the billing/limit implications clarified up front. Confidence: 0.45
- Security/exposure-conscious: probes what a tool can reach and do — who else can access or invoke it when it's publicly reachable ("can anyone in the world text it too?"), and what it can touch on their own machine and how it handles credentials ("latch is just a local mcp server that can get pwds and then use them to run some sort of command on my mac?") — including the data-flow of local access, i.e. how an agent actually reaches local info and what then leaves the machine ("explain also how it can let an agent access my local info") — and wants access restrictions/exposure documented. Confidence: 0.45
- Repeatedly tries to pin an unfamiliar concept down in their own words — either a confirm-style question ("wait so … is just …?") or by re-asking for it as a fill-in-the-blank definition ("ok so explain what latch is.. a local mcp server that …") — and expects the premise corrected precisely and a crisp, restatable one-sentence definition rather than polite agreement or lengthy prose ("means its just running an applescript to gab messages and thn the mcp skill filters" → premise corrected: sending is AppleScript, reading is a bundled CLI). Confidence: 0.5
- When told about an enumerated field or option set, wants the complete list of possible values ("owner is one — are there others?") — documentation should enumerate every value and its meaning, not just the common/primary one. Confidence: 0.5
- Wants the ground truth, not a paraphrase: when told a capability exists, asks where the actual source lives ("where can i read those skills") and is best served by concrete links to the real upstream files and the exact commands they document — and then wants those pointers captured in the docs themselves as reference material ("document pointers to those as reference docs so i can read them"). Confidence: 0.5
- Portability/lock-in conscious: when a platform offers a built-in service (e.g. hosted LLM inference), asks whether that's optional or mandatory ("can i use any llm provider or does plow provide compute inference easily too?") — expects docs to state both the platform-provided route and the bring-your-own alternative (own provider/keys/local model), and to be explicit about which parts are fixed vs. their choice. Confidence: 0.55
- Keeps secrets out of version control and build artifacts: when initializing a repo, expects the credentials file to be gitignored (and not baked into images), and instead wants a checked-in template/example file (e.g. `plow-credentials.example`) so others can set it up. Confidence: 0.6
- Wants example/config template files to be heavily commented — explaining how to set each value up, where each value comes from, and how it is produced or rotated — not just key placeholders. Confidence: 0.6
- Never wants code attribution in git commits: no `Co-authored-by:` trailers, no bot/tool/assistant credit lines — commit messages must contain only the message body itself. Confidence: 0.85
- Wants agent/tool configuration applied at both scopes: globally in the user's `~/.commandcode/` (explicitly asks for "a global one too in USER" so the rule covers every project) and committed at the project level (e.g. a shared, checked-in `.commandcode/settings.json`) so it travels with the repo for anyone who clones it. Confidence: 0.6
- Knows and expects the `~/.commandcode/` file layout to be respected: `config.json` for CLI-managed preferences (provider, model, theme) and `settings.json` for hooks, permissions, and MCP — settings must land in the semantically correct file rather than being dumped anywhere that parses. Confidence: 0.5
- Wants git repos to use `main` as the branch name, not `master` — explicitly calls this out before committing and expects it enforced (e.g. `git branch -M main` / making `main` the default for new repos). Confidence: 0.75
- Questions heavyweight frameworks/dependencies by default ("why do I need X", "can I roll my own super small one") — leans toward minimal, self-contained implementations and understanding the underlying protocol/wire contract over batteries-included defaults; explicitly declines the batteries-included default in favor of a "lightweight compatible" alternative. Confidence: 0.7
